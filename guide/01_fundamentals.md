## 一、基础概念（10 题）

### 1. AI Agent 和普通 Chatbot / LLM 的本质区别是什么？

**核心结论：「自主闭环执行」vs「单次无状态推理」。**

| 维度 | Chatbot / LLM | AI Agent |
|------|--------------|----------|
| 核心能力 | 文本生成、问答 | 规划 + 工具使用 + 记忆 + 自主纠错 |
| 执行模式 | 单次输入 → 单次输出（无状态） | 思考 → 行动 → 观察 → 再思考（Agentic Loop） |
| 环境交互 | 仅文本界面 | 调用 API、操作数据库、浏览器、物理设备 |
| 失败处理 | 用户重试 | 自主重试、换工具、重规划 |
| 记忆 | 仅上下文窗口 | 短期工作记忆 + 长期向量/键值存储 |

**别背表格，建议这样讲：**

> 我理解两者最本质的差别不是“有没有工具”，而是**是否对结果负责**。普通 Chatbot 更像一次性回答问题，回答完就结束；Agent 更像一个执行体，拿到目标后会自己拆步骤、调用工具、检查结果，失败了还要决定是重试、换路径还是求助人。

**为什么这个回答更像“理解”而不是“定义”：**
- 你抓的是“责任边界”和“闭环能力”，不是名词堆砌
- 面试官继续追问时，你能自然展开到规划、工具、记忆、护栏，而不是重新背概念
- 这也能解释为什么有些“会调工具”的系统还不算成熟 Agent，因为它没有稳定的闭环执行能力

**标准回答示例：**

> 我理解 AI Agent 和普通 Chatbot 的本质区别，不是表面上会不会调用工具，而是它是不是一个对任务结果负责的执行闭环。普通 Chatbot 更像一次性的问答系统，用户问一句，它回一句，答错了通常还是用户自己重问；但 Agent 拿到的是目标，不是单轮问题，所以它要自己拆步骤、选工具、检查执行结果，必要时还要重试或者重新规划。从工程角度看，我会把 Agent 理解成“带状态、带行动能力、带纠错机制的任务执行体”，而不只是更聪明的聊天机器人。

**加分项：** 引入可量化的「自主决策步数」（如复杂任务平均需 5-8 步），说明 Agent 不是在"聊天"而是在"完成任务"。

### 2. Agent 的核心组件有哪些？

- **感知层（Perception）**：组装上下文（用户输入 + 记忆 + 工具描述 + 系统提示）
- **推理/规划层（Reasoning/Planning）**：生成执行计划，选择行动策略
- **工具执行层（Action/Actuator）**：调用 API、代码执行、浏览器操作、数据库查询
- **记忆层（Memory）**：工作记忆 + 情景记忆 + 语义记忆 + 过程记忆
- **评估/护栏层（Guardrails）**：校验输出合法性、预算/步数限制、安全策略
- **编排器（Orchestrator/Controller）**：状态机或图结构，管理步骤流转和错误恢复

**理解重点：** 不要把这些组件背成“模块清单”，要把它们看成一个生产系统里必须拆开的责任边界。真正上线时，最容易出问题的往往不是模型本身，而是上下文装配、工具执行、状态恢复和护栏缺失。

**标准回答示例：**

> 我一般把 Agent 拆成六层来看：感知层负责把用户输入、记忆、检索结果和工具描述组装成上下文；规划层负责决定接下来做什么；执行层真正去调工具；记忆层负责跨步骤和跨会话保留信息；护栏层负责限制风险，比如预算、权限和结果校验；最外面还需要一个编排器来管理状态流转和异常恢复。这样拆的好处是，每一层的故障都能被定位，比如工具调用错了，不一定是模型笨，也可能是 schema 设计有问题，或者编排器没有做重试和回滚。

### 3. Agentic Loop（智能体循环）完整流程是什么？

```
用户目标 → 感知(Perceive) → 规划(Plan) → 执行(Act) → 观察(Observe) → 评估(Evaluate) → 循环或终止
```

关键：这是一个**闭环**，每次循环会重新感知（含上一步观察结果），产生新的思考和行动。

**白板演示技巧：** 画圆环图，标注每步的输入输出类型（Perceive 输出 Context，Plan 输出 Steps，Act 输出 Observation）——比平铺文字更有说服力。

**理解重点：** Agentic Loop 的核心价值不在“多走几步”，而在每一步都能根据环境反馈修正下一步。这意味着它更像控制系统，而不是更长的 Prompt。

**标准回答示例：**

> 我会把 Agentic Loop 理解成一个带反馈的控制闭环，而不是简单的多轮对话。它先感知当前上下文，再做规划，然后执行动作，拿到观察结果后重新评估下一步要不要继续、重试还是终止。这里最关键的是 Observe 和 Evaluate，因为没有这两步，系统就只是按预设流程往下跑，出了错也不知道。我做系统设计时会特别关注每一轮循环输出什么状态、记录什么日志、什么条件下触发 replanning，这样 Agent 才不会变成一个失控的 while loop。

### 4. Agent 和 RAG 的关系是什么？Agent 一定需要 RAG 吗？

- RAG 是 Agent 的知识增强手段之一，但不是必需的
- Agent 可以只有工具调用而无检索（如纯 API 编排类 Agent）
- Agent + RAG = 让 Agent **自主决策**何时检索、检索什么、用什么知识库，而非固定管道
- 两者正交：RAG 解决「知识从哪里来」，Agent 解决「怎么一步步达成目标」

**理解重点：** 很多人会把 Agent 和 RAG 混成一件事，但它们解决的是不同问题。一个负责“知识补给”，一个负责“任务编排”。

**标准回答示例：**

> 我的理解是，RAG 和 Agent 是两个正交能力。RAG 解决的是模型知识不够新、不够全的问题，让系统能够从外部知识库里取信息；Agent 解决的是任务怎么被拆解和执行的问题，它决定什么时候该查、查完之后怎么用、下一步是继续检索还是调用工具。所以 Agent 不一定需要 RAG，比如纯 API 编排任务就可以没有检索；反过来，传统 RAG 也不一定是 Agent，因为它可能只是固定的“检索后回答”流水线。真正有价值的是 Agentic RAG，也就是把检索从固定步骤变成可被策略化决策的一步。

### 5. 什么样的任务适合用 Agent 而不是传统方案？

| 适合 Agent | 不适合 Agent |
|------------|-------------|
| 多步推理 + 外部工具调用的复合任务 | 单轮确定性问答 |
| 目标不明确、需要探索性执行 | 输入输出高度标准化 |
| 跨系统编排（查 API A → 填表单 B → 发邮件 C） | 纯文本生成或翻译 |
| 需要自主纠错和回退 | 实时性要求极高（<100ms） |
| 长周期任务，中间可能有环境变化 | 安全敏感场景，不允许任何误操作 |

**理解重点：** 判断要不要用 Agent，关键不是“它看起来高级”，而是任务是否存在不确定性、跨系统性和反馈闭环需求。

**标准回答示例：**

> 我会用一个很工程化的标准判断任务适不适合 Agent：第一，它是不是多步的；第二，中间是不是要和外部系统交互；第三，执行过程中环境会不会变化；第四，失败后值不值得让系统自己修正。如果这几个条件同时满足，比如查数据、生成方案、调用多个系统再回填结果，这类任务很适合 Agent。反过来，如果只是一个确定性的分类、抽取或者翻译问题，我一般不会上 Agent，因为那样只会增加延迟、成本和不稳定性。

### 6. Agent 常见的失败模式有哪些？

| 失败模式 | 表现 | 根因 |
|----------|------|------|
| 无限循环 | 反复调用同一工具、无进展 | Planner 缺乏收敛信号 |
| 工具幻觉 | 调用不存在的 API 或参数虚构 | 工具描述模糊，LLM 自由发挥 |
| 目标漂移 | 偏离最初目标，越做越偏 | 缺乏中间验证点 |
| 记忆膨胀 | 上下文过长导致「迷失在中间」 | 无限追加历史，无压缩策略 |
| 级联错误 | 一步错导致后续全错 | 无中间检查点与回滚机制 |
| 过早终止 | 尚未完成就宣称成功 | 成功标准模糊 |

**理解重点：** 失败模式背后其实对应的是系统设计缺口。说清“失败现象”和“系统缺口”的映射关系，会显得你真的做过。

**标准回答示例：**

> 我见过的 Agent 失败大多不是模型单点失误，而是系统没有把失败当成常态来设计。比如无限循环通常说明没有收敛条件，工具幻觉通常说明 tool schema 和权限边界不够明确，目标漂移说明没有阶段性验收点，记忆膨胀说明没有压缩和淘汰策略。所以我看失败模式时，不会只说“模型不稳定”，而是会把它落到具体机制上：哪里缺 checkpoint，哪里缺验证，哪里缺 budget control，哪里缺中间态观测。

### 7. Agent 中的「自主性」如何分级？

| 级别 | 描述 | 示例 |
|:----:|------|------|
| L1 | 人类操作，AI 仅建议 | 给出操作建议，人不执行 |
| L2 | AI 执行，人类确认 | 生成计划，人审批后执行 |
| L3 | AI 自主执行，人类可中断 | 自主订机票，超预算时暂停 |
| L4 | 高度自主，人类监督异常 | 自动运维，异常告警人工介入 |
| L5 | 完全自主 | 全自动量化交易（极少见） |

面试中要强调：**绝大多数生产系统在 L2-L3，HITL（Human-in-the-Loop）是标配而非缺陷。**

**标准回答示例：**

> 我不会把自主性简单理解成“越高越好”，因为生产里真正重要的是风险和收益是否匹配。大多数企业系统其实落在 L2 到 L3，也就是 AI 可以做规划和执行，但关键节点还要有人确认，或者至少人能随时中断。像发消息、提 PR、改配置这种动作可以逐步放开，但涉及支付、删库、生产变更的事情，我会默认放回 HITL。换句话说，自主性不是炫技指标，而是权限设计问题。

### 8. 解释 ReAct 模式的核心思想。

Reasoning + Acting 交替执行：

```
Thought: 我需要知道北京的天气和机票价格
Action: search_weather("北京")
Observation: 晴，25°C
Thought: 天气没问题，查机票
Action: search_flights("北京→上海", "2025-06-15")
Observation: 最低 ¥680
Thought: 价格可接受，下一步查酒店
...
```

**优势：** 灵活，适合探索性任务。**劣势：** Token 消耗大，每一步都要 LLM 推理一次。

**理解重点：** ReAct 真正厉害的地方不是“会想”，而是把推理暴露成一个可被观察和纠错的中间层。

**标准回答示例：**

> 我会把 ReAct 理解成一种“边想边做”的策略，而不是单纯输出 Thought 和 Action 两段文字。它的价值在于，模型不是一次性给最终答案，而是每走一步都基于当前观察结果更新判断，所以特别适合信息不完整、需要探索的任务。它的代价也很明显，就是 token 和时延会上去，所以如果任务本身路径比较确定，我可能会更偏向先规划后执行，而不是每一步都重新推理。

### 9. 什么是结构化输出（Structured Output）？为什么 Agent 必须用？

- 强制 LLM 输出 JSON / YAML 等格式化数据，而非自由文本
- 下游解析器可**确定性**处理，不会因措辞变化而崩溃
- 工具调用的参数必须从结构化输出中提取
- 面试加分点：提到 JSON Schema 约束 + 解析容错 + 重试机制三层保障

**理解重点：** 结构化输出不是“格式更好看”，而是把概率模型接到确定性系统时，降低接口不稳定性的必要手段。

**标准回答示例：**

> 在 Agent 里我会把结构化输出看成硬约束，而不是可选优化。因为一旦模型输出要被下游程序直接消费，比如拿去调工具、写数据库、创建工单，如果还是自由文本，系统就会非常脆弱。真正生产可用的做法通常是三层：先用 schema 约束输出形状，再做程序级校验和容错解析，最后对失败样本做重试或降级。这样回答的重点是，你不是为了“规范格式”，而是为了让概率模型和确定性执行系统之间的接口稳定下来。

### 10. 你在 Agent 项目中遇到过什么坑？怎么解决的？

面试官想听的不是「遇到过什么坑」，而是**系统化排查和解决的能力**。推荐回答结构：

> 问题 → 现象 → 根因分析（工具/代码/模型/数据四维度排查）→ 方案 → 量化效果

**高频坑举例：**
- 「工具调用 JSON 格式不稳定」→ 加 Schema 约束 + Pydantic 校验 + 3 次重试，成功率从 82% → 99.6%
- 「记忆膨胀导致 128K 上下文截断」→ 滚动摘要 + TTL 淘汰，平均步数减少 30%

**理解重点：** 这题最怕答成“我遇到 bug 然后修了 bug”。真正要体现的是你怎么定位问题、怎么做因果拆分、怎么量化结果。

**标准回答示例：**

> 我一般会挑一个能体现系统性思考的坑来讲。比如我们之前遇到过工具调用成功率不稳定的问题，表面现象是模型偶尔输出错参数，但我没有直接归因给模型，而是先拆成四层排查：是不是 schema 描述不清、是不是 prompt 约束不够、是不是解析器太脆、还是工具本身返回不一致。最后发现主要问题是接口约束太弱，于是我加了 JSON Schema、Pydantic 校验和失败重试，并把失败样本单独打日志回放。这样回答的重点不是“我修了一个 bug”，而是我展示了完整的问题定位链路和量化效果。
