## 十二、训练微调与对齐（10 题）

### 1. 什么时候该微调，什么时候用 Prompt Engineering？

| 维度 | Prompt Engineering | Fine-tuning |
|------|-------------------|-------------|
| 迭代速度 | 分钟级 | 小时-天级 |
| 成本 | 几乎为零 | GPU 成本 + 数据标注成本 |
| 可控性 | 中等（长 Prompt 被截断） | 高（模型内部化） |
| 适用 | 行为调整、简单格式控制 | 领域特化、复杂行为模式 |
| Token 消耗 | 每次都要注入 Prompt | 一次训练，省 Token |

**决策树：**
```
改行为 → 先试 Prompt → 3 轮 Prompt 调不好 → 收集 100+ 条 bad case → 微调
```

**标准回答示例：**

> 我通常先问问题是“知识不够”还是“行为模式不稳”，如果只是规则、格式和流程问题，我优先用 prompt 和上下文工程；如果是稳定风格、工具调用能力或领域分布明显不同，才考虑微调。

### 2. LoRA / QLoRA 的原理和区别？

**LoRA（Low-Rank Adaptation）：**
- 冻结原模型权重，在旁路添加低秩矩阵（A×B）训练
- 参数量 ~0.1% 原模型，训练快、显存低

**QLoRA：**
- LoRA + 4bit 量化 + NF4 格式 + 双重量化 + 分页优化器
- 在 48GB GPU 上可微调 65B 模型（LoRA 需要 780GB）

**面试要说的：** NF4 是 4bit 非均匀量化，信息密度高于均匀量化；双重量化是对量化因子本身再量化。

**标准回答示例：**

> 我会把 LoRA 理解成低成本适配大模型，而 QLoRA 是在更低显存下把这件事做得更经济。它们重要的不是公式，而是把微调门槛从大集群降到更现实的工程条件。

---

### 3. 全参数微调 vs LoRA 怎么选？

| 场景 | 推荐 |
|------|------|
| 领域差异大（如从通用到医疗） | 全参数 |
| 格式/风格调整 | LoRA |
| 数据少（<1K 条） | LoRA |
| 数据多（>10K 条） | 全参数 |
| 显存有限 | QLoRA |
| 需要多次快速迭代 | LoRA（可合可拆） |

**标准回答示例：**

> 全参数微调适合领域迁移很大、预算也足够的场景；LoRA 更适合做格式、风格和流程能力的增强。我的判断标准主要是目标变化幅度和可承受成本。

### 4. DPO 相比 RLHF 的优缺点？

| 维度 | RLHF | DPO |
|------|------|-----|
| 训练流程 | SFT → 训奖励模型 → PPO 优化 | 直接在偏好对上优化 |
| 复杂度 | 高（3 阶段） | 低（1 阶段） |
| 稳定性 | PPO 训练不稳定 | 稳定 |
| 奖励建模 | 需训练独立奖励模型 | 隐式奖励，无需额外模型 |
| 在线学习 | 支持（持续收集反馈） | 仅离线 |

**DPO 适用：** 数据充足、对齐目标明确的场景。**RLHF 适用：** 需要在线持续优化的场景。

**标准回答示例：**

> DPO 的优势在于更简单直接，工程上更容易跑起来；RLHF 则更灵活，但链路更长、更容易不稳定。面试里我会强调这其实是“训练成本和控制能力”的取舍。

### 5. 什么是奖励破解（Reward Hacking）？如何检测？

**现象：** Agent 找到「奖励模型给高分但实际无意义」的捷径。

**案例：** 奖励「输出长度 → Agent 疯狂重复同一句话凑字数」。

**检测：**
- 奖励值异常飙升但人工评估下降
- KL 散度突然增大（策略偏离参考模型）
- 特殊模式频繁出现（如规避关键词、过度礼貌用语）

**缓解：** KL 惩罚、多奖励模型 ensemble、人工抽查。

**标准回答示例：**

> 奖励破解本质上是模型学会了“骗指标”，而不是真的学会了任务。检测它的关键是把训练目标和真实业务目标分开看，找那些高分但明显不合理的轨迹。

### 6. 过程监督 vs 结果监督有什么区别？

| 维度 | 结果监督（Outcome） | 过程监督（Process） |
|------|-------------------|---------------------|
| 标注内容 | 最终答案对错 | 每一步推理是否正确 |
| 标注成本 | 低 | 高（每步都标） |
| 效果 | 好答案可能坏过程 | 训练更稳定的推理链 |
| 代表工作 | RLHF | OpenAI o1, PRM（过程奖励模型） |

**趋势：** 过程监督在复杂推理（数学、代码）任务上显著优于结果监督。

**标准回答示例：**

> 我会把结果监督理解成只看最后答得对不对，过程监督则会约束它中间是怎么得到这个结果的。对多步推理和 Agent 任务来说，过程监督通常更稳。

### 7. 合成数据（Synthetic Data）在 Agent 训练中怎么用？

**应用场景：**

| 用途 | 方法 |
|------|------|
| 工具调用数据 | 用强模型（如 GPT-4）生成多样化工具调用示例 |
| 错误恢复数据 | 注入工具失败 → 记录 Agent 如何恢复 → 作为训练数据 |
| 多步推理数据 | STaR：Agent 自己尝试 → 正确路径保留 → 错误路径修正 |
| 偏好数据 | 同一任务，生成好/坏两种执行，人工标注偏好 |

**风险：** 模型崩溃（Model Collapse）——用合成数据训练的模型可能丢失多样性。对策：混合真实数据。

**标准回答示例：**

> 合成数据的价值不只是补量，而是补困难样本、边界样本和稀有场景。前提是你要有过滤机制，不然很容易把错误模式一起放大。

### 8. 如何微调一个更好的 Function Calling 模型？

**数据构造：**

```
Single-turn Function Call:
  User: "北京今天天气怎么样？"
  Assistant: {"tool": "get_weather", "args": {"city": "北京", "date": "今天"}}

Multi-turn with Tool Results:
  User: "北京和上海哪个更热？"
  Assistant: {"tool": "get_weather", "args": {"city": "北京"}}
  Tool: {"temp": 25}
  Assistant: {"tool": "get_weather", "args": {"city": "上海"}}
  Tool: {"temp": 28}
  Assistant: "上海更热，28°C vs 25°C"
```

**关键：** 数据要覆盖「工具选择错误 → 重试」和「工具返回异常 → 降级」等边界情况。

**标准回答示例：**

> 微调 Function Calling 模型时，我最关注的是 schema 遵从率、参数填充准确率和工具选择稳定性。因为这类能力最终都是接口可靠性问题。

### 9. 什么是宪法 AI（Constitutional AI）？

**Anthropic 提出的对齐方法：**

1. 用一份「宪法」（规则清单，如「不生成有害内容」「尊重隐私」）指导模型
2. 模型根据宪法自我批评，生成修正版回复
3. 用（原回复，修正回复）作为偏好数据训练

**优势：** 减少人工标注依赖，规则可解释、可审计、可更新。

**标准回答示例：**

> 宪法 AI 在我看来是把对齐原则显式化，让模型在训练和推理里都有更稳定的行为边界。它的价值不是“更道德”这么空，而是更可控、更可审计。

### 10. 微调后的模型如何评估是否退化？

| 维度 | 评估方法 |
|------|----------|
| 通用能力 | 在标准基准（MMLU、HellaSwag）上对比微调前后 |
| 灾难性遗忘 | 原任务上的性能是否下降 >3% |
| 目标能力 | 微调目标任务的指标是否达标 |
| 过拟合 | 训练集和测试集差距是否 >10% |
| 安全性 | 红队测试是否新引入漏洞 |

**标准回答示例：**

> 评估微调后是否退化，不能只看目标任务是否提升，还要看通用能力、幻觉率、拒答行为和工具稳定性有没有被破坏。因为很多模型是某一项变强了，但整体更脆了。
