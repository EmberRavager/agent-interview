# 2026 Agent 开发工程师近期线上题库补充

> 调研时间：2026-06-13  
> 适用岗位：AI Agent 开发工程师 / LLM Agent 工程师 / AI 应用工程师 / Agent 平台工程师 / Coding Agent 工程师

这份补充题库不是直接复制网上面经原文，而是基于近期公开资料、官方文档、论文趋势和岗位高频要求重新整理，适合作为 `2026 Agent 开发面试` 的专项速刷材料。

重点趋势：

- 面试已经从“Agent 是什么”转向“怎么把 Agent 做稳定、可观测、可恢复、可控成本地上线”。
- `MCP / Tool Calling / OpenAPI Tool / A2A` 会越来越常被问。
- `Memory / Context Engineering / Session / State` 不再只是概念题，容易变成系统设计题。
- `Eval / Trace / Trajectory / Tool Use` 是生产落地能力的核心考点。
- `Sandbox / 权限 / 人审 / Prompt Injection / Tool Poisoning` 是 Agent 安全高频点。
- Coding Agent、Browser Agent、Workflow Agent 会被拿来考工程架构和边界控制。

## 1. Agent 基础与架构

### Q1：Agent 和普通 Chatbot 的核心区别是什么？

**考察点：** 是否理解 Agent 的自主执行闭环。

**回答抓手：**

普通 Chatbot 主要是一次或多轮对话生成；Agent 是围绕目标执行任务的系统，通常包含 `LLM 决策 + 工具调用 + 状态管理 + 观察反馈 + 终止条件`。真正的工程差异不是“会不会聊天”，而是能否在约束条件下安全地调用外部工具、处理失败、恢复状态、输出可验证结果。

**追问：**

- Agent Loop 怎么设计？
- 什么时候不应该用 Agent？
- Agent 失败后怎么恢复？

---

### Q2：一个生产级 Agent 最少需要哪些模块？

**考察点：** 系统化架构能力。

**回答抓手：**

至少包括：输入理解、任务规划、工具注册与调用、上下文管理、状态存储、执行器、错误处理、权限控制、日志追踪、评估体系、人工介入机制。业务复杂后还需要模型路由、成本控制、缓存、限流、审计和灰度发布。

---

### Q3：Agent Loop 一般怎么终止？

**考察点：** 是否知道 Agent 不能无限自主执行。

**回答抓手：**

常见终止条件包括：任务完成、达到最大步数、达到最大 token 或成本预算、工具连续失败、置信度不足、触发安全规则、需要用户确认。工程上一般会设置 `max_steps`、`max_tool_calls`、`timeout`、`budget` 和 `human_escalation`。

---

### Q4：Agent 的“自主性”越强越好吗？

**考察点：** 安全边界和业务取舍。

**回答抓手：**

不是。自主性越强，错误传播、成本失控、权限滥用和不可解释风险越大。生产系统通常不会追求完全自治，而是根据任务风险分层：低风险任务自动执行，中风险任务执行前确认，高风险任务只给建议不直接操作。

---

### Q5：你怎么判断一个需求该用 Workflow、RAG 还是 Agent？

**考察点：** 架构选型能力。

**回答抓手：**

- 流程固定、规则明确：优先 Workflow。
- 主要是知识问答和引用来源：优先 RAG。
- 任务多步、路径不确定、需要动态选择工具：考虑 Agent。
- 任务高风险、强合规：Agent 只能作为辅助，关键动作需要人审。

---

### Q6：Agent 和传统后端服务最大的工程差异是什么？

**回答抓手：**

传统服务的控制流主要由代码决定，Agent 的部分控制流由模型输出决定，所以需要额外处理不确定性，包括输出结构校验、工具参数校验、轨迹审计、失败重试、回滚、人审和评估。

---

### Q7：Agent 系统里的状态应该存在哪里？

**回答抓手：**

短期上下文可以放在会话上下文或 session store；长期记忆需要独立存储，例如数据库、向量库、搜索索引或对象存储；任务执行状态应该放在可恢复的状态机、队列或工作流引擎中，不能只依赖模型上下文。

---

### Q8：Agent 平台和单个 Agent 应用有什么区别？

**回答抓手：**

单个 Agent 应用面向具体业务流程；Agent 平台提供通用能力，比如模型接入、工具注册、权限、编排、调试、观测、评估、发布、版本管理、租户隔离和成本统计。

---

## 2. Tool Calling / Function Calling / MCP

### Q9：Function Calling 的本质是什么？

**回答抓手：**

Function Calling 不是模型真的执行函数，而是模型根据工具 schema 生成结构化调用参数，再由宿主程序执行函数并把结果返回给模型。核心在于 schema 设计、参数校验、权限控制、错误处理和结果回传。

---

### Q10：Tool Calling 为什么需要 schema？

**回答抓手：**

schema 用来约束模型输出，让工具参数结构化、可校验、可解析。没有 schema，模型容易输出自然语言描述，后端很难稳定执行。生产中还要对 schema 做必填字段、枚举、类型、范围和业务规则校验。

---

### Q11：工具调用失败后 Agent 应该怎么处理？

**回答抓手：**

要区分失败类型：参数错误可以让模型修正参数；网络错误可以重试；业务错误要返回明确原因；权限错误不能自动绕过；高风险失败要中断并转人工。所有失败都应该进入 trace 和 eval 样本。

---

### Q12：MCP 解决了什么问题？

**回答抓手：**

MCP 提供了模型应用连接外部工具、数据源和上下文的一套标准协议。它把 Host、Client、Server 分离，降低不同模型和不同工具之间的重复集成成本，适合做 IDE、知识库、业务系统和工具生态连接。

---

### Q13：MCP 里的 Tools、Resources、Prompts 有什么区别？

**回答抓手：**

- Tools：模型可以调用的函数或动作。
- Resources：可读取的上下文或数据，例如文件、数据库记录、文档。
- Prompts：可复用的提示词模板或工作流入口。

回答时要强调：Tool 是动作，Resource 是上下文，Prompt 是模板。

---

### Q14：MCP Tool 和普通 Function Calling 有什么区别？

**回答抓手：**

Function Calling 通常是某个模型 API 内的工具调用能力；MCP 更像通用连接协议，定义了客户端和服务端如何发现工具、调用工具、返回结果、处理资源和授权。MCP 的重点是生态互操作和工具服务化。

---

### Q15：MCP 有哪些安全风险？

**回答抓手：**

主要包括：恶意工具描述诱导模型误用、Prompt Injection、Tool Poisoning、越权访问资源、工具组合导致数据外泄、服务器伪装、用户未授权操作。工程上要做工具白名单、权限分级、确认弹窗、最小权限、审计日志和敏感操作人审。

---

### Q16：为什么工具描述本身也不一定可信？

**回答抓手：**

因为工具描述可能来自第三方服务，攻击者可以在描述中写入诱导模型泄露数据或调用危险工具的指令。模型容易把描述当作上下文执行，因此工具描述应该被视为不可信输入，不能覆盖系统安全策略。

---

### Q17：如何设计一个稳定的工具注册中心？

**回答抓手：**

需要包含工具元数据、schema、版本、权限、调用方式、超时、重试、幂等配置、风险等级、负责人、审计开关和测试用例。工具上线前要通过 schema 校验、沙箱测试和安全审核。

---

### Q18：Tool Calling 如何做幂等？

**回答抓手：**

对会产生副作用的工具，比如发邮件、下单、删除文件，要引入幂等 key、请求去重、状态检查、执行前确认和结果持久化。Agent 重试时不能重复执行副作用动作。

---

### Q19：什么时候需要强制 Tool Calling？什么时候不能强制？

**回答抓手：**

必须查实时数据、业务数据、权限数据时可以强制调用工具；开放式写作、总结、解释类任务不一定需要。不能为了“显得智能”强制调用工具，否则会增加延迟、成本和失败点。

---

### Q20：OpenAPI Tool 和 MCP Tool 怎么选？

**回答抓手：**

已有标准 REST API、接口比较稳定时，用 OpenAPI Tool 很方便；需要跨应用暴露工具、资源、提示词，或者希望让不同 Agent 客户端复用工具服务时，更适合 MCP。企业内部可以两者结合：OpenAPI 描述业务接口，MCP 做 Agent 连接层。

---

## 3. RAG 与 Agentic RAG

### Q21：传统 RAG 和 Agentic RAG 的区别是什么？

**回答抓手：**

传统 RAG 通常是一次检索、一次生成；Agentic RAG 会让模型参与检索策略，比如查询改写、多轮检索、工具选择、结果反思、是否继续检索、是否需要调用数据库或 API。区别在于检索路径是否动态决策。

---

### Q22：RAG 为什么不能完全解决幻觉？

**回答抓手：**

RAG 只提供外部上下文，模型仍可能误读材料、忽略证据、混合旧信息和新信息，或者在证据不足时强行回答。因此要做引用、答案约束、拒答策略、检索质量评估和生成后校验。

---

### Q23：RAG 系统怎么评估？

**回答抓手：**

至少分三层：检索评估、生成评估、端到端业务评估。检索看 recall、precision、MRR、nDCG；生成看 groundedness、faithfulness、answer correctness；业务看解决率、人工转接率、用户满意度和延迟成本。

---

### Q24：向量检索和 BM25 怎么选？

**回答抓手：**

BM25 对关键词、专有名词、错误码、精确匹配更强；向量检索对语义相似、同义表达更强。生产中常用混合检索，再用 reranker 重排。Agent 记忆场景里还要考虑低延迟和增量索引。

---

### Q25：为什么 Agent 记忆不应该只用向量库？

**回答抓手：**

向量库适合语义召回，但不擅长表达结构化状态、时间顺序、权限边界、任务状态和确定性事实。长期记忆通常需要结构化数据库、搜索索引、事件日志和向量库组合。

---

### Q26：RAG 数据权限怎么做？

**回答抓手：**

不能把所有文档混到一个无权限向量库里。应该在索引和检索阶段都保留 ACL、租户、部门、文档级权限，查询时按用户权限过滤。答案生成阶段还要避免把无权限内容泄露出来。

---

### Q27：RAG 文档切片怎么设计？

**回答抓手：**

要根据文档结构、业务语义和问答粒度设计。常见策略包括按标题层级切、按段落切、滑动窗口、父子 chunk、表格单独处理。切片太小会丢上下文，太大会降低召回精度和增加 token 成本。

---

### Q28：怎么处理 RAG 里的过期知识？

**回答抓手：**

要保留文档版本、更新时间、来源、有效期和优先级。检索时优先新版本，生成时显示来源和日期。对制度、价格、接口文档这类高时效数据，需要定期重建索引或实时查询源系统。

---

### Q29：Agentic RAG 为什么容易成本失控？

**回答抓手：**

因为它可能多轮查询改写、多次检索、多次 rerank、多次模型判断，还可能调用外部工具。需要限制最大检索轮数、最大工具调用数、token 预算、缓存和早停策略。

---

### Q30：如何设计一个企业知识库 Agent？

**回答抓手：**

架构可以是：用户问题 → 权限识别 → 查询改写 → 混合检索 → rerank → 证据选择 → 生成带引用答案 → 置信度判断 → 低置信转人工或继续检索。生产要补日志、反馈、评估集、权限审计和增量索引。

---

## 4. Memory / Context Engineering

### Q31：短期记忆和长期记忆的区别是什么？

**回答抓手：**

短期记忆服务当前任务，通常来自当前会话、最近消息、工具结果和临时状态；长期记忆跨会话保留，通常包括用户偏好、历史事实、项目上下文和任务结果。短期记忆强调上下文完整，长期记忆强调可检索、可更新、可遗忘和权限安全。

---

### Q32：Context Engineering 和 Prompt Engineering 有什么区别？

**回答抓手：**

Prompt Engineering 更关注提示词怎么写；Context Engineering 更关注每次模型调用时应该放入哪些信息、以什么结构放入、如何压缩、如何排序、如何过滤、如何控制 token 和权限。Agent 里 Context Engineering 更重要。

---

### Q33：上下文太长怎么办？

**回答抓手：**

常见做法包括：摘要压缩、滑动窗口、重要性打分、基于任务的选择性召回、工具结果裁剪、结构化状态外置、长文档按需 lazy-load。不能简单把所有历史都塞进上下文。

---

### Q34：长期记忆如何更新？

**回答抓手：**

需要判断什么信息值得长期保存，并区分事实、偏好、任务状态和临时信息。更新时要支持去重、冲突解决、时间戳、来源、置信度和删除机制。敏感信息需要显式授权。

---

### Q35：Agent 记忆怎么评估？

**回答抓手：**

可以看四类能力：准确检索、跨多轮理解、测试时学习、选择性遗忘。工程指标包括记忆命中率、错误记忆率、过期记忆召回率、隐私泄露率和对任务完成率的提升。

---

### Q36：为什么工具结果不能全部长期保存？

**回答抓手：**

工具结果可能包含临时数据、敏感数据、过期数据或噪声。长期保存前要做摘要、脱敏、有效期、权限和价值判断，否则会污染记忆并造成隐私风险。

---

### Q37：多轮 Agent 怎么避免“上下文漂移”？

**回答抓手：**

需要维护明确的任务目标、当前状态、已完成步骤、待办步骤、约束条件和失败记录。每轮执行前重建结构化上下文，而不是盲目拼接所有聊天记录。

---

### Q38：Session、State、Memory 三者怎么区分？

**回答抓手：**

Session 是一次会话或任务运行的容器；State 是当前任务的结构化状态；Memory 是可跨会话复用的信息资产。Session 偏运行时，State 偏任务进度，Memory 偏长期知识。

---

### Q39：Agent 的上下文里应该放哪些内容？

**回答抓手：**

优先放任务目标、用户约束、关键历史、当前状态、可用工具、最近工具结果、安全规则和必要业务数据。不要放无关历史、过长原文、无权限数据和未验证的工具描述。

---

### Q40：如何做个人助理 Agent 的长期记忆？

**回答抓手：**

要分层存储：用户偏好、联系人、日程习惯、项目上下文、历史任务结果。每条记忆有来源、时间、置信度和可删除能力。涉及隐私和敏感数据时需要用户可见、可控、可撤销。

---

## 5. Planning / Reasoning / Tool Scheduling

### Q41：ReAct 的核心思想是什么？

**回答抓手：**

ReAct 是让模型在推理和行动之间交替：先分析当前任务，再选择动作或工具，获得观察结果后继续下一步。它适合工具调用和探索型任务，但需要限制步数和处理错误循环。

---

### Q42：Plan-and-Execute 和 ReAct 有什么区别？

**回答抓手：**

Plan-and-Execute 先生成整体计划，再按步骤执行；ReAct 是边想边做、边观察边调整。前者适合目标清晰、步骤较稳定的任务；后者适合信息不完整、需要动态探索的任务。

---

### Q43：什么时候需要 Replanning？

**回答抓手：**

当工具结果和预期不一致、用户约束变化、外部环境变化、某一步失败或发现更优路径时，需要重新规划。工程上要记录失败原因和新旧计划差异，避免无限重规划。

---

### Q44：Tool Planning 和 Tool Scheduling 有什么区别？

**回答抓手：**

Tool Planning 关注选哪些工具、为什么选；Tool Scheduling 关注工具调用顺序、并行还是串行、依赖关系和效率。复杂任务里，选对工具不够，还要安排正确执行顺序。

---

### Q45：工具调用可以并行吗？

**回答抓手：**

可以，但要看工具之间是否有依赖。互不依赖的查询类工具可以并行，能降低延迟；有状态依赖、副作用或顺序约束的工具不能随便并行。并行调用要处理超时、部分失败和结果合并。

---

### Q46：Agent 如何避免陷入无效循环？

**回答抓手：**

设置最大步数、重复动作检测、相同工具参数去重、连续失败中断、计划进度检查、置信度阈值和人工介入。还可以让模型定期输出当前进度和剩余目标，辅助判断是否继续。

---

### Q47：Reflection 在 Agent 中有什么作用？

**回答抓手：**

Reflection 用来让 Agent 对执行过程进行自检，比如判断计划是否合理、工具结果是否支持结论、是否需要补充检索。它可以提升复杂任务质量，但也会增加成本和延迟，不能滥用。

---

### Q48：如何设计一个任务规划器？

**回答抓手：**

规划器输入是目标、约束、可用工具、当前状态和历史结果；输出是可执行步骤、依赖关系、终止条件和风险等级。执行过程中要支持步骤状态更新、失败重试、重新规划和人工确认。

---

## 6. Multi-Agent / Handoff / Workflow Graph

### Q49：多 Agent 一定比单 Agent 好吗？

**回答抓手：**

不一定。多 Agent 增加了通信成本、状态同步、责任边界和调试难度。只有当任务天然有角色分工、并行处理、专家协作或权限隔离需求时，才值得引入多 Agent。

---

### Q50：Handoff 和 Agent-as-Tool 有什么区别？

**回答抓手：**

Agent-as-Tool 更像主 Agent 调用一个子 Agent 完成子任务，控制权仍在主 Agent；Handoff 是把对话或任务控制权转交给另一个 Agent，适合客服、专家路由和多角色协作。

---

### Q51：多 Agent 怎么避免互相甩锅？

**回答抓手：**

要定义清晰职责、输入输出 schema、任务所有者、超时策略、失败归因和最终仲裁者。复杂系统里通常需要一个 coordinator 或 workflow engine 管理流程，而不是让 Agent 自由聊天。

---

### Q52：Workflow Graph 和自由 Agent Loop 怎么选？

**回答抓手：**

流程稳定、风险较高、需要可审计时用 Workflow Graph；任务开放、路径不确定时用 Agent Loop。生产系统常用混合模式：主流程用图控制，局部节点用 Agent 做动态决策。

---

### Q53：多 Agent 协作有哪些通信方式？

**回答抓手：**

常见方式包括中心协调、黑板模式、消息队列、事件总线、共享状态存储、直接对话、工具调用。工程上要避免长对话互相污染，最好用结构化消息和状态同步。

---

### Q54：如何设计一个研究报告多 Agent 系统？

**回答抓手：**

可以拆成：Planner、Searcher、Reader、Verifier、Writer、Editor。Planner 拆任务，Searcher 找资料，Reader 提取证据，Verifier 校验事实，Writer 写稿，Editor 做风格和结构。关键是证据链和引用，不是 Agent 数量。

---

### Q55：多 Agent 的可观测性怎么做？

**回答抓手：**

需要记录每个 Agent 的输入、输出、工具调用、状态变化、耗时、token、错误和父子任务关系。Trace 要能还原完整执行链路，方便定位哪个 Agent 做错了哪一步。

---

### Q56：Agent 路由怎么做？

**回答抓手：**

可以基于规则、分类模型、LLM 路由或向量匹配。生产中常用规则兜底 + 模型路由组合。路由结果要可解释，并且支持低置信度转人工或默认 Agent。

---

## 7. Evaluation / Observability

### Q57：为什么 Agent 评估比普通 LLM 评估更难？

**回答抓手：**

普通 LLM 多数只评估最终回答；Agent 还要评估中间轨迹，包括是否选对工具、参数是否正确、执行顺序是否合理、有没有多余调用、失败恢复是否正确。因此 Agent 评估要同时看过程和结果。

---

### Q58：Agent 的核心评估指标有哪些？

**回答抓手：**

包括任务完成率、工具调用准确率、轨迹匹配率、最终答案正确率、人工接管率、平均步数、延迟、token 成本、失败恢复率、安全违规率、用户满意度。

---

### Q59：什么是 Trajectory Evaluation？

**回答抓手：**

Trajectory Evaluation 是评估 Agent 完成任务过程中的动作序列，比如调用了哪些工具、顺序是否正确、参数是否正确、是否遗漏关键步骤。它比只看最终回答更适合发现 Agent 的过程错误。

---

### Q60：如何构建 Agent Eval 数据集？

**回答抓手：**

从真实日志、线上失败案例、人工设计用例和边界场景构建。每条样本包含用户输入、初始状态、期望工具轨迹、期望中间结果、最终答案和评分标准。线上新失败要持续回流到 eval 集。

---

### Q61：Agent 日志应该记录什么？

**回答抓手：**

记录用户请求、会话 ID、模型版本、prompt 版本、工具列表、工具调用参数、工具结果、状态变化、错误、耗时、token、成本、最终输出和安全拦截原因。敏感数据要脱敏。

---

### Q62：Trace 对 Agent 有什么价值？

**回答抓手：**

Trace 能还原完整执行链路，帮助定位模型决策错误、工具失败、上下文缺失、状态丢失、延迟瓶颈和成本异常。没有 trace 的 Agent 很难上线维护。

---

### Q63：如何做 Agent 的灰度发布？

**回答抓手：**

可以按用户、租户、流量比例、场景或风险等级灰度。对比新旧版本的任务完成率、成本、延迟、用户反馈和安全违规率。需要快速回滚和版本隔离。

---

### Q64：如何做 Agent 的线上监控告警？

**回答抓手：**

监控任务失败率、工具错误率、平均步数、超时率、token 成本、模型错误、拒答率、安全拦截率、人工接管率。异常时要能关联 trace 和具体工具。

---

### Q65：如何评估 Agent 是否“乱调用工具”？

**回答抓手：**

看工具调用是否必要、参数是否正确、是否重复调用、是否调用了高风险工具、是否违反权限、是否造成副作用。可以用规则 + 轨迹评估 + 人工抽检。

---

### Q66：为什么只看用户满意度不够？

**回答抓手：**

用户满意度滞后且主观，不能发现潜在安全问题、权限问题、成本问题和错误工具轨迹。Agent 评估必须结合离线 eval、线上指标、日志审计和人工质检。

---

## 8. Safety / Sandbox / Permission

### Q67：Agent 安全和普通 LLM 安全有什么区别？

**回答抓手：**

普通 LLM 主要风险是输出有害内容；Agent 还能调用工具、访问数据和执行动作，因此多了越权访问、错误操作、数据外泄、工具滥用和副作用执行风险。

---

### Q68：什么操作必须 Human-in-the-loop？

**回答抓手：**

涉及转账、下单、删除、发邮件、改权限、发公告、执行代码、访问敏感数据、影响多人或不可逆操作时，应要求用户确认或人工审批。

---

### Q69：Agent 沙箱主要解决什么问题？

**回答抓手：**

沙箱用于限制 Agent 执行代码、读写文件、访问网络和调用系统资源的范围，防止恶意代码、误操作和越权访问。Coding Agent、Browser Agent、数据分析 Agent 都需要沙箱或隔离环境。

---

### Q70：Prompt Injection 对 Agent 为什么更危险？

**回答抓手：**

因为 Agent 会读取外部网页、文档、邮件或工具结果，这些内容可能包含恶意指令。如果模型把外部内容当作高优先级指令执行，就可能泄露数据或调用危险工具。

---

### Q71：如何防 Prompt Injection？

**回答抓手：**

需要做指令分层、外部内容隔离、工具权限控制、敏感信息过滤、引用来源标记、危险动作确认、输出校验和审计。不要让网页或文档内容覆盖 system/developer 规则。

---

### Q72：什么是最小权限原则？

**回答抓手：**

Agent 只获得完成当前任务所需的最小工具、最小数据和最小操作权限。权限应按用户、任务、工具、资源和风险等级动态控制，而不是给 Agent 全量后台权限。

---

### Q73：如何设计工具权限模型？

**回答抓手：**

可以按工具风险分级：只读工具、低风险写工具、高风险写工具、不可逆工具。再叠加用户权限、租户权限、场景权限、审批策略和审计策略。

---

### Q74：Agent 泄露敏感信息怎么防？

**回答抓手：**

输入侧做数据分级和权限过滤；上下文构建时避免放入无关敏感数据；工具结果做脱敏；输出侧做 DLP 检测；日志中做脱敏存储；高风险场景要求人工审核。

---

### Q75：如何处理 Agent 的越权工具调用？

**回答抓手：**

工具执行层必须做权限校验，不能只相信模型判断。即使模型生成了调用参数，后端也要根据用户身份、资源权限、工具风险等级和审批状态决定是否执行。

---

### Q76：Agent 安全审计要记录什么？

**回答抓手：**

记录谁在什么时间、以什么身份、让哪个 Agent、调用了哪个工具、访问了哪些资源、参数是什么、结果是什么、是否经过审批、是否触发安全策略。

---

## 9. Production / MLOps / 成本控制

### Q77：Agent 上线最容易出的问题有哪些？

**回答抓手：**

常见问题包括工具失败、模型输出不稳定、上下文丢失、延迟过高、token 成本失控、权限漏洞、缺少 trace、评估集不足、Prompt 版本混乱和线上问题难复现。

---

### Q78：Agent 如何控制成本？

**回答抓手：**

可以通过模型路由、小模型优先、缓存、上下文压缩、限制最大步数、减少无效工具调用、批处理、异步执行、结果复用、按风险选择模型和监控 token 成本来控制。

---

### Q79：模型路由怎么设计？

**回答抓手：**

根据任务复杂度、风险等级、延迟要求、成本预算和模型能力选择模型。简单分类和格式化任务用小模型，复杂规划和高风险判断用强模型。路由策略需要评估和回滚。

---

### Q80：Agent 如何做版本管理？

**回答抓手：**

要管理 prompt 版本、工具版本、模型版本、schema 版本、评估集版本和 workflow 版本。每次上线都能追溯到具体版本组合，并支持回滚。

---

### Q81：如何保证 Agent 输出结构稳定？

**回答抓手：**

使用 JSON schema、Pydantic、严格输出格式、后处理校验、失败重试和默认兜底。关键业务不能直接相信模型自然语言输出。

---

### Q82：Agent 的失败重试怎么设计？

**回答抓手：**

要区分模型失败、工具失败、网络失败、业务失败和安全失败。可恢复错误可以重试，不可恢复错误要中断；有副作用操作必须幂等；多次失败要转人工或降级。

---

### Q83：Agent 如何降级？

**回答抓手：**

模型不可用时切换备用模型；工具不可用时返回部分结果或人工处理；RAG 失败时提示无法确认；复杂 Agent 失败时退回固定流程或 FAQ。降级不能假装成功。

---

### Q84：如何让 Agent 问题可复现？

**回答抓手：**

保存输入、上下文、prompt 版本、模型版本、采样参数、工具 schema、工具返回、状态快照和 trace。必要时对工具结果做快照，保证离线复现。

---

## 10. Coding Agent / Browser Agent / Data Agent

### Q85：Coding Agent 的核心架构是什么？

**回答抓手：**

通常包括代码仓库上下文、文件检索、计划生成、代码编辑、测试执行、错误修复、diff 展示、权限控制和提交机制。关键是沙箱执行和可回滚，不是只让模型写代码。

---

### Q86：Coding Agent 为什么需要读 repo 上下文？

**回答抓手：**

因为代码修改依赖项目结构、已有接口、类型定义、测试约定和业务风格。只看用户需求容易写出孤立代码。需要结合检索、静态分析、测试和编译反馈。

---

### Q87：Coding Agent 如何避免误删代码？

**回答抓手：**

要使用 diff 审核、文件白名单、测试校验、版本控制、人工确认和回滚机制。高风险修改不能自动提交，尤其是删除文件、改数据库脚本、改权限配置。

---

### Q88：Browser Agent 的难点是什么？

**回答抓手：**

网页环境动态、元素变化、登录态复杂、反爬限制、视觉理解误差、操作不可逆。需要可视化 trace、步骤确认、DOM/截图结合、超时重试和敏感操作人审。

---

### Q89：Data Analysis Agent 怎么保证结果可信？

**回答抓手：**

需要记录数据来源、SQL、筛选条件、计算过程、图表生成代码和结果解释。对关键指标做校验，避免模型直接编数字。最好让 Agent 输出可执行分析脚本和证据链。

---

### Q90：视频生成 Agent 可以怎么设计？

**回答抓手：**

可以拆成选题 Agent、脚本 Agent、分镜 Agent、素材 Agent、生成 Agent、质检 Agent、发布 Agent。重点是工作流状态、资产管理、失败重试、人工审核和平台发布权限。

---

## 11. 系统设计题

### Q91：设计一个企业客服 Agent。

**回答框架：**

入口层接入 IM/网页；理解层识别意图和用户身份；知识层做权限过滤 RAG；工具层查询订单、工单和用户信息；决策层判断自动回答、调用工具或转人工；观测层记录 trace、满意度、解决率和失败样本。高风险动作如退款、改地址要人审。

---

### Q92：设计一个 Agent 编排平台。

**回答框架：**

核心模块包括 Agent 配置、工具注册、Workflow 编排、模型路由、会话状态、权限控制、运行时执行、日志 trace、评估集、发布灰度、成本统计。平台重点是把不确定的模型行为纳入确定的工程约束。

---

### Q93：设计一个知识库问答 Agent。

**回答框架：**

文档接入 → 清洗切片 → 权限索引 → 混合检索 → rerank → 证据压缩 → 生成引用答案 → 置信度判断 → 反馈回流。重点讲权限、引用、过期文档、评估和拒答。

---

### Q94：设计一个 Coding Review Agent。

**回答框架：**

接入 PR diff、仓库上下文、代码规范、历史问题和测试结果；Agent 识别风险代码、调用静态分析工具、生成 review 建议；输出必须带文件行号、原因、风险等级和修复建议。避免泛泛而谈。

---

### Q95：设计一个 K8s 告警分析 Agent。

**回答框架：**

接入 Prometheus/Grafana/日志系统/K8s API；输入告警后查指标、事件、日志和最近发布；输出根因候选、证据链、影响范围、处理建议。危险操作如重启、扩容、回滚需要人工确认。

---

### Q96：设计一个 TikTok 视频生成发布 Agent。

**回答框架：**

包括热点采集、选题评分、脚本生成、分镜生成、素材/模型调用、视频质检、标题标签、定时发布和数据回流。发布权限、人审、素材版权和失败重试是关键。

---

### Q97：设计一个个人助理 Agent。

**回答框架：**

需要日程、邮件、联系人、任务、记忆和工具权限。低风险查询自动完成；发邮件、改日程、转账等高风险动作确认。长期记忆必须可见、可修改、可删除。

---

### Q98：设计一个多 Agent 研究报告系统。

**回答框架：**

Planner 拆任务，Researcher 搜索资料，Extractor 抽取证据，Verifier 校验事实，Writer 生成报告，Editor 优化表达。关键是引用、事实校验、冲突来源处理和最终人工审核。

---

### Q99：设计一个 MCP 工具市场。

**回答框架：**

包括工具发布、schema 校验、权限声明、风险评级、版本管理、调用统计、安全扫描、用户授权、审计和下架机制。工具描述不能完全可信，执行层必须做权限控制。

---

### Q100：设计一个 Agent 评估平台。

**回答框架：**

支持导入真实日志、构造 eval case、定义期望工具轨迹、运行多模型对比、统计任务完成率、工具准确率、成本和延迟。线上失败自动进入候选评估集，形成 Eval Flywheel。

---

## 12. 面试回答模板

### 12.1 回答 Agent 系统设计题

```text
我会先拆成 6 层：
1. 入口和身份：用户是谁，有什么权限；
2. 上下文：需要哪些历史、知识库、业务数据；
3. 决策：用 Workflow 还是 Agent Loop，是否需要规划；
4. 工具：有哪些工具，schema、权限、幂等、超时怎么做；
5. 安全：哪些动作需要确认，怎么防 Prompt Injection；
6. 观测评估：trace、任务完成率、工具准确率、成本和失败回流。
```

### 12.2 回答 Agent 生产问题

```text
我不会只从 prompt 层面解决，而会从运行时约束解决：
- 限制最大步数和最大工具调用；
- 工具参数做 schema 和业务校验；
- 副作用工具做幂等和人审；
- 每次运行保留 trace；
- 线上失败进入 eval 集；
- 通过灰度和回滚控制风险。
```

### 12.3 回答 MCP 相关题

```text
MCP 的价值是把模型应用和外部工具/数据源之间的连接标准化。
但它不是只解决调用问题，也带来安全问题：
工具描述、资源内容、第三方 server 都可能是不可信输入。
所以 MCP 落地时必须配合授权、工具白名单、用户确认、审计和最小权限。
```
