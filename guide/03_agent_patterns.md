## 三、Agent 设计模式（10 题）

### 1. ReAct 和 Plan-then-Execute 怎么选？

| 维度 | ReAct | Plan-then-Execute |
|------|-------|-------------------|
| 控制流 | 思考-行动交替，不可预测 | 先出完整计划，再逐步执行 |
| 灵活度 | 高，能应对意外 | 低，但可预测可审计 |
| Token 消耗 | 高（每步都推理） | 低（只规划一次） |
| 适用场景 | 探索性、信息不完整 | 结构化、步骤已知 |
| 失败恢复 | 自然重试 | 需显式 rollback |

**面试金句：** 「结构化任务用 Plan-Execute 省 Token，不确定性高用 ReAct 保证灵活性。我们线上做了一个路由器——90% 简单任务走 Plan-Execute，复杂任务自动切换 ReAct。」

**标准回答示例：**

> 我不会把这两个模式看成谁更先进，而是看任务不确定性高不高。探索型任务我更偏 ReAct，因为它能边观察边调整；结构化任务我更偏 Plan-then-Execute，因为更省 token，也更容易审计和回放。

### 2. 什么是 Reflection / Reflexion？如何避免过度反思？

**Reflection：** Agent 执行完一步后，对自己的输出进行自我批判，发现问题后重新生成。

**Reflexion：** 进阶版，将反思结果存入长期记忆，后续类似任务自动避坑。

**避免过度反思的三板斧：**
1. 最大反思轮次限制（如 3 轮）
2. 反思触发条件：只有置信度低 / 结果被 Verifier 拒绝 / 与预期偏差大时触发
3. 反思内容减量：只记录「哪里错了 + 怎么改」，不重复全部上下文

**标准回答示例：**

> 我的理解是反思机制的价值在于默认第一次结果可能不够可靠，但它不能无限触发，否则系统会掉进高成本低收益的自我循环。真正合理的是只在高风险节点加轻量复核。

### 3. CodeAct 模式和传统 Tool-Use 有什么区别？

**CodeAct：** Agent 通过写代码来执行操作，而非调用预定义工具。

| 比较 | Tool-Use | CodeAct |
|------|----------|---------|
| 执行方式 | 匹配预定义工具 + 填参 | 直接生成 Python/SQL/Shell |
| 灵活性 | 受工具列表限制 | 理论上无限 |
| 安全性 | 工具可审计 | 沙箱必须严格 |
| Token 效率 | 多次工具调用 | 一段代码批量操作 |

**典型场景：** 数据分析（pandas 一次性加载-清洗-聚合）比多次函数调用高效太多。

**标准回答示例：**

> CodeAct 和普通 Tool-Use 的差别，在于它把代码本身当成可执行中间语言，所以灵活性更高。代价是你必须把沙箱、依赖环境和状态管理做好，不然能力越强风险越大。

### 4. Chain-of-Thought (CoT) 和 Tree-of-Thoughts (ToT) 的区别？

| 方法 | 结构 | 适用场景 |
|------|------|----------|
| CoT | 单链推理 | 数学、逻辑等有标准路径的问题 |
| ToT | 多分支树探索 + 剪枝 | 需要搜索最优解的问题（如游戏策略） |
| GoT (Graph) | 图结构，可合并分支 | 复杂推理，多路径融合 |

**Agent 中怎么用：** 规划阶段用 ToT 探索多条路径，执行阶段用 CoT 保持高效。

**标准回答示例：**

> CoT 更像沿一条路径往下推理，ToT 则会展开多个候选思路再做搜索和选择。所以上限通常是 ToT 更高，但成本也更大，我只会在复杂搜索类任务里用它。

### 5. 什么是 Toolformer？它的训练方式有什么特别之处？

- **Toolformer（Meta 2023）**：让 LLM 自监督学会何时以及如何调用工具
- 核心创新：在文本语料中**自动标注**工具调用插入点，无需人工标注
- 训练流程：生成候选工具调用 → 执行工具 → 用自回归损失筛选有效调用 → SFT

**为什么重要：** 它是第一个真正让 LLM「学会」使用工具而非被 Prompt 驱动的工作，启发了后续 Function Calling 机制。

**标准回答示例：**

> 我会把 Toolformer 理解成让模型在训练阶段就学会什么时候值得用工具，而不是完全依赖推理时提示词。它很有启发，因为说明工具使用既可以是编排层逻辑，也可以成为模型习得的能力。

### 6. ReWOO 是什么？相比 ReAct 有什么优势？

ReWOO（Reasoning WithOut Observation）：

- ReAct 每步都要等 Observation 再推理，串行慢
- ReWOO 一次性生成完整计划（含所有工具调用），**并行执行**后汇总
- Token 消耗更少（减少 Observation → Thought 的冗余推理）

**适用场景：** 工具调用无相互依赖时，ReWOO 可大幅提速。

**标准回答示例：**

> ReWOO 的本质价值是先把依赖关系想清楚，再执行具体动作，所以比纯 ReAct 更节省 token，也更适合长链任务。它适合路径相对稳定的任务，不太适合强探索型场景。

### 7. DEPS（Describe-Explain-Plan-Select）模式是什么？

DEPS 是面向复杂推理任务的模式：

1. **Describe**：描述当前状态
2. **Explain**：解释当前状态与目标的差距
3. **Plan**：规划下一步
4. **Select**：选择具体行动

比 ReAct 多了一个 **Explain** 步骤，强制 Agent 自我解释，降低幻觉和跳跃推理。

**标准回答示例：**

> DEPS 更像一种防止模型一上来就乱做的思考框架，先描述问题、解释约束，再规划和选择动作。它的本质作用是提升问题建模质量，而不是单纯换一个 Prompt 模板。

---

### 8. LLM Compiler 和普通 Agent 的区别是什么？

LLM Compiler（Berkeley 2024）将 Agent 执行过程类比为代码编译：

- 每个工具调用类比为指令
- 通过**依赖分析**自动识别可并行的工具调用
- 生成 DAG 而非线性序列，最大化并发

**面试亮点：** 「我们的调度器参考了 LLM Compiler 的思路，工具调用自动生成 DAG，无依赖的并行执行，平均耗时降低 40%。」

**标准回答示例：**

> 我会把 LLM Compiler 讲成把自然语言需求编译成执行图，重点是依赖分析、并行调度和执行优化。这个思路特别像传统编译器，所以也更容易和工程系统结合。

### 9. 如何为 Agent 设计 Fallback 策略？

三层降级：

```
L1: 正常执行 → L2: 简化执行（减少工具/步骤） → L3: 静态兜底回复
```

- L1：完整 Agent 执行，所有工具可用
- L2（L1 失败）：降级为有限工具集 + 减少步数，快速产出部分结果
- L3（L2 失败）：返回预置回复 + 引导人工

**为什么重要：** Agent 的可靠性不是「成功率」而是「最差情况下的用户体验」。

**标准回答示例：**

> Fallback 不是“失败了再试一次”，而是提前设计好多层退路，比如换工具、换模型、缩短流程或转人工。高分点在于你把失败当成常态设计，而不是出了问题才补救。

---

### 10. 你的 Agent 项目用了什么设计模式？为什么？

面试必问题。回答结构：

> 场景 → 为什么选这个模式 → 效果数据

**示例：** 「做数据查询 Agent 时，用户问题有 70% 是单步 SQL 查询（结构化），30% 是多步分析（需要探索）。我设计了路由器：先用小模型分类，简单查询走 Plan-Execute（秒级响应），复杂分析走 ReAct + CodeAct。上线后 P50 延迟从 8s 降到 1.2s。」

**标准回答示例：**

> 如果问我项目用了什么模式，我会优先讲组合，比如“规划 + 执行 + 轻量反思 + 护栏”，再讲为什么这么配。这样更像真实系统设计，而不是贴一个框架标签就结束。
