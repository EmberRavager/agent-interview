## 四、工具调用与 Function Calling（10 题）

### 1. Function Calling 的完整流程是什么？

```
定义工具 Schema → 注入 System Prompt → LLM 输出工具调用 JSON → 
解析 JSON → 参数校验 → 执行工具 → 结果回注上下文 → 继续推理
```

**面试要强调的两点：**
- 不是 LLM 直接调用函数，而是 LLM 输出 JSON，由外部框架执行
- 结果回注是关键——Agent 能否利用工具结果是区分好坏 Agent 的核心

**标准回答示例：**

> 我会把 Function Calling 理解成“模型负责决定调什么，程序负责确定性执行”，中间靠 schema 对齐接口。真正生产里关键不是吐出 JSON，而是参数校验、结果回注和异常处理。

---

### 2. 如何设计一个「生产可用」的工具？

**六大原则：**

1. **JSON Schema 严格定义** → 参数类型、枚举值、必填项明确，禁止 anyOf 宽泛定义
2. **描述精简但完整** → 100-300 tokens，说清干什么、入参出参、副作用
3. **分级错误处理** → 瞬态错重试 / 确定性错降级 / 阻断性错 HITL
4. **幂等性标注** → GET/SEARCH 幂等可重试，POST/DELETE 非幂等需谨慎
5. **动态注册** → 支持运行时工具增删，配合工具版本管理
6. **响应格式统一** → `{success, data, error, metadata}` 标准结构

**标准回答示例：**

> 在我看来，生产级工具最重要的不是多，而是边界清楚、参数稳定、错误可解释、权限可控。否则模型一旦高频调用，系统会很快因为接口脆弱而不稳定。

---

### 3. 工具调用的 JSON 输出不稳定怎么办？

**三层保障体系：**

| 层级 | 手段 | 效果 |
|------|------|------|
| L1 约束 | JSON Schema + structured output API | 格式正确率 ~95% |
| L2 容错 | 正则提取 + 括号补全 + 字段默认值 | 覆盖 ~4% 小错误 |
| L3 重试 | 错误信息反馈 LLM，要求修正 | 最终 >99.5% |

**加分回答：** 「我们统计了 10 万次工具调用，最常见的 3 个格式错误是：缺少闭合括号（32%）、字段名拼写错误（24%）、参数值类型错误（18%）。针对性做了模糊解析。」

**标准回答示例：**

> 这类问题我不会只怪模型，而会从 schema 设计、提示约束、解析容错和重试机制一起看。因为结构化输出稳定性本质上是模型和程序之间的接口设计问题。

---

### 4. 工具选择（Tool Selection）怎么做？怎么避免选错工具？

**策略演进：**

| 代 | 方式 | 问题 |
|:--:|------|------|
| 1 代 | 全量工具描述全注入 Prompt | Token 爆炸，选错率高 |
| 2 代 | 两阶段：先分类检索候选工具，再精确匹配 | 分类器可能不准 |
| 3 代 | 语义向量检索 + Rerank | 当前主流 |
| 4 代 | 动态路由：小模型初筛 → 大模型确认 | Token 最优 |

**降低选错率的关键：** 工具描述中加负例说明（「本工具不适用于 XXX 场景」）。

**标准回答示例：**

> 工具选择本质是路由问题，重点不只是模型知不知道这个工具，而是它知不知道什么时候该用、什么时候不该用、多个候选里怎么选最合适的那个。好的工具描述通常比堆更多工具更重要。

---

### 5. 工具调用的并行 vs 串行如何决策？

**决策树：**

```
有数据依赖？
  ├─ 是 → 串行（必须等前一步结果）
  └─ 否 → 可以并行
       └─ 工具之间有副作用冲突？
            ├─ 是 → 串行（如先查再删）
            └─ 否 → 并行（如同时查天气、汇率、新闻）
```

**进阶：** 用依赖分析（类似 LLM Compiler）自动构建 DAG，最大化并行度。

**标准回答示例：**

> 我判断并行还是串行主要看依赖关系和副作用，如果两个工具互不依赖且风险低，就尽量并行提速；如果后一步依赖前一步结果，或者有顺序约束，就必须串行。这样回答会更工程化。

---

### 6. 工具执行超时怎么处理？

**三级超时策略：**

1. **软超时（如 5s）**：返回部分结果 + 警告，Agent 自己决定是否接受
2. **硬超时（如 30s）**：强制终止，返回 timeout error
3. **预算超时（如整个任务 60s）**：所有工具共用时间预算，消耗完返回 PartialResult

**面试要提：** 超时后给 Agent 的提示必须包含「已获取的部分结果」和「未完成的部分」，让 Agent 做知情决策。

**标准回答示例：**

> 我会把超时视为常规工程问题，所以会提前设计 timeout、重试、熔断和降级。尤其长任务里，超时后能不能从 checkpoint 恢复，比单纯“再等等”更重要。

---

### 7. 什么是工具调用的「幻觉」？如何防范？

**工具幻觉：** LLM 捏造不存在的工具名、参数或端点。

**防范四层：**

- **编译时检查**：工具白名单，调用前验证工具名和 Schema
- **沙箱执行**：所有工具调用在受限环境中执行，无法越权
- **结果校验**：工具返回后验证格式和数据合法性
- **熔断器**：同一工具连续 3 次调用失败（格式错、返回空），自动降级

**标准回答示例：**

> 工具幻觉通常不是一句“模型乱编”就能解释完，它本质上说明模型的可行动边界太宽。防它的核心是白名单、schema 校验和权限控制，而不是只靠提示词提醒。

### 8. MCP（Model Context Protocol）和传统 Function Calling 的区别？

| 维度 | Function Calling | MCP |
|------|-----------------|-----|
| 定位 | 单次调用机制 | 客户端-服务器协议 |
| 标准化 | 各家 LLM API 自行实现 | 开放标准（Anthropic 提出） |
| 工具发现 | 硬编码或简单注册 | 动态服务发现 |
| 协议原语 | 主要是函数/参数 | Tools + Resources + Prompts |
| 传输方式 | 依附模型厂商 API | 基于 JSON-RPC 的有状态连接，支持多种 transport |
| 多 Agent | 不直接支持 | 支持工具/资源/提示共享，可作为 Agent runtime 的基础设施 |
| 生态 | 封闭 | 开放生态，便于“一次接入，多端复用” |

**面试金句：** 「MCP 像 AI 世界的 USB-C——一个接口，即插即用所有工具。」

**追问加分点：**
- Server 侧核心能力不止 `tools`，还包括 `resources` 和 `prompts`
- Client 侧还可能提供 `sampling`、`roots`、`elicitation`
- 真正的难点不在“能不能调通”，而在授权、边界控制、审计和远程连接安全

**标准回答示例：**

> 我会说 Function Calling 更像单次调用接口，MCP 更像长期连接协议，它不只暴露 tools，还暴露 resources 和 prompts。真正差别在生态和工程抽象层级，而不只是调用格式。

---

### 9. 如何设计一个工具调用网关？

```
Agent → Tool Gateway → Auth → Rate Limiter → Router → Tool Executor → Response
                             ↓                    ↓
                        Permission DB        Tool Registry
```

**关键模块：**
- **认证鉴权**：每个工具按 Agent/User 粒度授权
- **限流**：防止 LLM 疯狂调用，预算用尽自动降级
- **路由**：支持工具版本管理 + 灰度发布
- **审计**：全量工具调用日志，用于复盘和计费

**标准回答示例：**

> 我会把工具网关类比成 API Gateway，它的职责是鉴权、限流、路由、审计和版本管理。这样讲的好处是能把 AI 系统问题翻译成熟悉的后端架构问题。

---

### 10. 设计一个支持动态注册的工具系统。

```
Tool Registry (etcd/Redis):
  tool:weather_search → {schema, endpoint, version, status, cost_per_call}
  
Tool Discovery:
  1. Agent 启动 → 拉取工具列表（过滤可用+有权限的）
  2. 运行时新增工具 → Watch 机制实时通知

Tool Invocation:
  1. Agent 输出工具调用 JSON
  2. Gateway 验证：工具是否存在 / 版本兼容 / 权限
  3. 转发到对应 Executor
  4. 结果回注 + 审计日志
```

**追问：** 「工具下线怎么处理？」→ 软下线（标记 deprecated + 警告），过渡期结束硬下线。已在执行的 Agent 不受影响，新 Agent 不可见。

**标准回答示例：**

> 动态注册工具系统的重点不是“加工具快”，而是加了之后还能被发现、授权、观测和回滚。否则工具越多，系统只会越来越混乱，而不会越来越强。
