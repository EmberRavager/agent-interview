## 八、多 Agent 协作（10 题）

### 1. 什么时候需要多 Agent 而非单 Agent？

**必须用多 Agent 的场景：**

| 场景 | 原因 |
|------|------|
| 专业化分工 | 前端 Agent 不能写后端代码，需要 Coder Agent |
| 并行加速 | 同时搜索多个平台比价 |
| 博弈/辩论提升质量 | 两个 Agent 互相挑战对方的逻辑 |
| 异构能力 | 文本 Agent + 图像 Agent + 语音 Agent 协作 |
| 安全隔离 | 高危操作由独立 Agent 执行 + 审计 |

**不需要多 Agent：** 简单任务、单步查询、确定性高的问题——多 Agent 的通信开销可能大于收益。

**标准回答示例：**

> 我不会默认多 Agent 一定比单 Agent 强，只有当任务天然可拆分、角色边界清晰、单 Agent 上下文压力太大时，多 Agent 才值得引入。否则你得到的往往只是更多通信成本和更多故障点。

### 2. 多 Agent 通信协议如何设计？

**最小协议：**

```json
{
  "from": "planner",
  "to": "coder",
  "type": "task",
  "id": "task-42",
  "content": "写一个 Python 函数处理 CSV",
  "context": {...},
  "deadline": "2025-06-15T10:00:00Z",
  "priority": "high"
}
```

| 消息类型 | 用途 |
|----------|------|
| Task | 分配任务 |
| Result | 返回结果 |
| Query | 请求信息 |
| Critique | 审查/质疑 |
| Status | 进度同步 |

**标准回答示例：**

> 多 Agent 通信本质上是分布式系统问题，所以我会优先讲消息格式、状态同步、超时和幂等，而不是只说“它们互相聊天”。能把这层讲清楚会很加分。

### 3. Planner-Subagent 架构的细节是什么？

```
User Goal
    ↓
Planner Agent (分解任务，分配子任务)
    ↓
┌───────┬───────┬───────┐
│ Coder │Search │Browser│  ← Subagents
└───────┴───────┴───────┘
    ↓
Merger Agent (汇总结果，检查一致性)
    ↓
Final Output
```

**关键设计决策：**
- Subagent 之间是否互相可见？默认隔离，降低耦合
- Planner 是否等待所有 Subagent？可设置超时 + 部分汇总
- 失败是否重分配？Subagent 失败可换人或降级

**标准回答示例：**

> 我理解 Planner-Subagent 的价值在于把“全局决策”和“局部执行”分开，这样主 Agent 不需要一次性背全世界。它特别适合复杂任务拆分，但前提是子任务边界要定义清楚。

### 4. 多 Agent 辩论模式如何提升输出质量？

```
Agent A 生成答案 → Agent B 审查挑刺 → Agent A 修正 → Agent C 裁判判定
```

**适用：** 需要高准确率的场景（医疗、法律、金融）。

**注意事项：**
- 辩论轮次限制（2-3 轮，再多边际收益递减）
- 裁判 Agent 需独立于辩论双方
- 有明确判定标准（不是「你觉得」而是「检查点 1/2/3 是否通过」）

**标准回答示例：**

> 多 Agent 辩论的本质不是热闹，而是用多视角互相揭错，提高高风险任务的鲁棒性。它适合关键判断，不适合所有任务都上，否则成本会很高。

### 5. 多 Agent 的冲突如何解决？

| 冲突类型 | 解决方案 |
|----------|----------|
| 资源竞争（同时调用同一工具） | 锁 + 队列 |
| 结论矛盾 | 仲裁 Agent + 置信度比较 |
| 优先级冲突 | 全局优先级队列，高优先先执行 |
| 信息不一致 | 同步共享工作记忆 |
| 死锁（A 等 B，B 等 A） | 超时 + 打破循环（如 A 升为 Master） |

**标准回答示例：**

> 我会把多 Agent 冲突当成调度问题来处理，比如资源锁、优先级、共享状态和仲裁机制。否则多个 Agent 一旦各自为政，很容易出现重复执行或结论打架。

### 6. 多 Agent 如何做负载均衡？

```
Task Queue (优先级排序)
    ↓
Dispatcher (根据 Agent 能力 + 当前负载分配)
    ↓
┌──────┬──────┬──────┬──────┐
│Agent1│Agent2│Agent3│Agent4│  ← Worker Pool
└──────┴──────┴──────┴──────┘
```

**分配策略：**
- 能力匹配（任务类型 → 擅长此任务的 Agent）
- 负载均衡（最少正在执行任务的 Agent 优先）
- 亲和性（同一用户的连续任务优先发给同一 Agent，减少记忆加载）

**标准回答示例：**

> 负载均衡不是简单轮询，而是能力匹配、当前负载和会话亲和性的组合。因为把任务发给“最闲的人”不一定比发给“最擅长的人”更优。

### 7. LangGraph、CrewAI、AutoGen 如何选型？

| 框架 | 调度模型 | 优势 | 劣势 |
|------|----------|------|------|
| LangGraph | 图/状态机 | 精细控制，可审计，生产级 | 学习曲线陡 |
| CrewAI | 角色扮演 | 上手快，概念直观 | 控制力有限 |
| AutoGen | 对话驱动 | 微软生态，灵活 | 文档一般 |
| OpenAI Swarm | 轻量级 | 极简，适合原型 | 功能有限 |

**面试建议：** 不用全都会，但至少深入用过 1 个，能说清楚为什么选它而不是另外两个。

**更像自己理解的回答方式：**

> 我选框架一般不先看“谁最火”，而是先看任务复杂度和我需要多少控制权。  
> 如果是要上线、要审计、要恢复执行，我更偏 LangGraph，因为图和状态机更容易管住流程；  
> 如果是快速验证多角色协作想法，CrewAI 会更快；  
> 如果我想把多 Agent 对话本身当成核心机制，AutoGen 会更自然。  
> 所以本质不是框架优劣，而是**控制力、抽象层级、交付速度**三者怎么取舍。

**这样回答的好处：**
- 显示你有选型方法，而不是只记产品名
- 面试官追问时，你可以顺势展开到状态机、可观测性、恢复执行、成本
- 听起来像做过项目，而不是看过对比博客

**标准回答示例：**

> 我选 LangGraph、CrewAI 还是 AutoGen，核心看的是控制力、抽象层级和交付速度，而不是谁更火。上线系统我更重控制和可审计，原型验证我更重效率。

### 8. 多 Agent 系统如何保证幂等性？

**幂等 = 同一操作执行多次结果一致。**

| 层面 | 措施 |
|------|------|
| 任务层 | 每个任务分配唯一 ID，执行前检查是否已完成 |
| 工具层 | 所有写操作先检查状态（如「创建文件」→ 检查文件是否已存在） |
| 消息层 | 消息去重（基于 message_id） |
| 状态层 | 状态机 + 幂等转换（如已支付 → 支付请求直接返回成功） |

**标准回答示例：**

> 多 Agent 系统里幂等尤其重要，因为网络重试、消息重复和多个 Agent 竞争执行都很常见。没有幂等，你很快就会遇到重复发消息、重复写库、重复创建资源的问题。

---

### 9. 多 Agent 系统的可观测性怎么设计？

**三层监控：**

| 层 | 指标 | 工具 |
|----|------|------|
| Agent 层 | 每个 Agent 的任务数、成功率、延迟 | LangSmith / 自研 |
| 通信层 | 消息数、错误率、延迟 | Kafka/消息队列监控 |
| 系统层 | CPU/内存/GPU/Token 消耗 | Prometheus + Grafana |

**分布式追踪：** 每个任务分配全局 trace_id，串联所有 Agent 的调用链。

**标准回答示例：**

> 多 Agent 可观测性的关键是 trace_id 和因果链，得能看清哪个 Agent 在什么上下文下做了什么决策。否则一旦出错，你连锅该算给谁都不知道。

### 10. 设计一个支持动态增减 Agent 的多智能体平台。

```
Agent Registry (etcd/Consul)
    ├── Agent-A (coder, status=active, capacity=10)
    ├── Agent-B (searcher, status=active, capacity=20)
    └── Agent-C (reviewer, status=active, capacity=5)

Task Router:
  1. Watch Agent Registry 变化
  2. 新 Agent 注册 → 加入可用池
  3. Agent 下线 → 标记 draining → 完成现有任务后移除
  4. 任务分配时：能力匹配 + 负载均衡

热更新：
  新版本 Agent 注册 → 旧版本标记 deprecated → 新任务路由到新版本 → 旧版本排空后下线
```

**标准回答示例：**

> 设计动态增减 Agent 的平台时，我会优先考虑注册、发现、权限、调度和生命周期管理。因为真正难的不是“能创建一个新 Agent”，而是创建之后还能稳定纳管。
