# 分布式 / 高并发 / Redis 队列面试题补充

> 调研时间：2026-06-13  
> 适用岗位：AI Agent 开发工程师 / Agent 平台工程师 / AI 应用后端工程师 / Java 后端工程师

这份补充题库用于补齐 Agent 工程师面试中容易被追问的后端基本功。很多 Agent 项目表面上是 LLM 应用，实际落地时一定会遇到高并发、异步任务、缓存、队列、分布式锁、幂等、限流、任务状态恢复和可观测性问题。

---

## 0. 为什么 Agent 面试也需要分布式和 Redis？

Agent 应用不是简单调用大模型 API，生产环境中经常会有这些问题：

- 用户请求量突然升高，模型调用和工具调用需要削峰。
- 视频生成、报告生成、代码扫描这类任务耗时长，需要异步队列。
- Agent 可能重复调用工具，需要幂等控制。
- 工具调用失败后需要重试、补偿和状态恢复。
- 热点用户、热点知识库、热点任务会造成缓存和数据库压力。
- 多个 worker 并发消费任务时，要避免重复执行和状态错乱。
- 高风险动作要串行化、加锁或人工确认。

一句话：**Agent 的智能上限看模型，工程下限看分布式系统能力。**

| 优先级 | 主题 | 为什么重要 |

## 2. Redis 缓存基础

### Q1：Redis 为什么快？

**回答抓手：**

Redis 主要快在：基于内存、单线程事件循环避免大量锁竞争、I/O 多路复用、高效数据结构、命令执行简单。需要注意：Redis 单线程指的是主要命令执行线程，不代表所有后台任务都是单线程。

**追问：**

- 单线程为什么还能高并发？
- Redis 6 之后多线程主要优化了什么？

---

### Q2：Redis 常见数据结构有哪些？分别适合什么场景？

**回答抓手：**

- String：缓存、计数器、分布式锁。
- Hash：对象缓存、用户信息、任务状态。
- List：简单队列。
- Set：去重、标签、共同好友。
- ZSet：排行榜、延迟队列。
- Stream：消息队列、消费组、异步任务流。
- Bitmap：签到、活跃状态。
- HyperLogLog：UV 统计。

---

### Q3：缓存和数据库怎么保持一致？

**回答抓手：**

常见策略是 Cache Aside：读时先查缓存，未命中查数据库再写缓存；写时先更新数据库，再删除缓存。删除缓存比更新缓存更常用，因为更新缓存可能写入旧值或增加复杂度。

**关键点：**

- 不能只说“先删缓存再写数据库”，容易出现并发脏数据。
- 高并发下可以用延迟双删、binlog 订阅、消息队列补偿。
- 对强一致要求高的场景不能只依赖缓存方案。

---

### Q4：什么是缓存穿透？怎么解决？

**回答抓手：**

缓存穿透是查询的数据缓存和数据库都不存在，请求每次都打到数据库。解决方法包括：缓存空值、布隆过滤器、参数校验、接口限流。

---

### Q5：什么是缓存击穿？怎么解决？

**回答抓手：**

缓存击穿是某个热点 Key 过期，大量并发请求同时打到数据库。解决方法包括：互斥锁重建缓存、热点 Key 不过期或逻辑过期、提前刷新、单飞机制。

---

### Q6：什么是缓存雪崩？怎么解决？

**回答抓手：**

缓存雪崩是大量 Key 同时失效，或者 Redis 整体不可用，导致请求压垮数据库。解决方法包括：过期时间加随机值、多级缓存、热点预热、Redis 高可用、限流降级、熔断保护。

---

### Q7：热点 Key 怎么发现和处理？

**回答抓手：**

发现方式：监控 QPS、慢日志、业务埋点、Redis hotkeys、网关访问统计。处理方式：本地缓存、多级缓存、Key 拆分、读写分离、提前预热、限流。

---

### Q8：大 Key 有什么危害？

**回答抓手：**

大 Key 会导致网络传输慢、阻塞 Redis 主线程、删除耗时、迁移困难、主从同步压力大。处理方式包括拆分 Key、分页读取、异步删除、限制 value 大小。

---

### Q9：Redis 缓存对象应该用 String 还是 Hash？

**回答抓手：**

如果对象整体读写，用 String 存 JSON 简单；如果字段级更新频繁，用 Hash 更合适。需要结合序列化成本、字段更新频率、内存占用和过期策略判断。

---

### Q10：缓存预热怎么做？

**回答抓手：**

系统启动或活动开始前，把热点数据提前加载到缓存。可以基于历史访问、运营配置、榜单、定时任务或发布流程做预热。预热失败要有监控和降级。

---

## 3. 分布式锁与幂等

### Q11：Redis 分布式锁怎么实现？

**回答抓手：**

基础实现是 `SET key value NX PX expireTime`，用 NX 保证不存在才设置，用 PX 设置过期时间。value 要用唯一 token，释放锁时用 Lua 脚本判断 token 一致再删除，避免误删别人的锁。

---

### Q12：为什么释放锁要用 Lua 脚本？

**回答抓手：**

因为判断锁是否属于自己和删除锁必须是原子操作。如果先 GET 再 DEL，中间锁可能过期并被别人获取，导致误删别人的锁。Lua 脚本可以保证原子性。

---

### Q13：Redis 分布式锁有什么问题？

**回答抓手：**

常见问题包括：业务执行时间超过锁过期时间、锁误删、Redis 主从切换导致锁丢失、网络分区、客户端 GC 暂停。高可靠场景不能只依赖简单 Redis 锁。

---

### Q14：锁过期但业务没执行完怎么办？

**回答抓手：**

可以设置合理过期时间、看门狗自动续期、拆短任务、状态机幂等、业务层校验。即使用了续期，也要保证业务本身幂等，不能把正确性完全压在锁上。

---

### Q15：Redisson 的看门狗机制是什么？

**回答抓手：**

Redisson 获取锁后，如果没有指定固定 leaseTime，会启动看门狗定期续期，防止业务没执行完锁就过期。它解决的是锁过早释放问题，但不能替代业务幂等和异常恢复。

---

### Q16：什么是接口幂等？

**回答抓手：**

同一个请求执行一次和执行多次，最终业务结果一致。幂等常用于支付、下单、发消息、任务执行、Agent 工具调用。常见方案包括唯一请求号、数据库唯一索引、状态机、Redis 去重、乐观锁。

---

### Q17：Agent 工具调用为什么需要幂等？

**回答抓手：**

Agent 可能因为模型重试、网络超时、工具失败重试而重复调用同一个工具。如果工具有副作用，比如发邮件、发布视频、扣库存、创建工单，就必须用幂等 key 防止重复执行。

---

### Q18：如何设计幂等 Key？

**回答抓手：**

幂等 Key 应该和业务动作绑定，比如 `userId + actionType + requestId + resourceId`。不能只用时间戳或随机数。幂等记录要有状态：处理中、成功、失败，并设置合理过期时间。

---

### Q19：分布式锁和幂等有什么区别？

**回答抓手：**

分布式锁控制并发进入临界区，幂等保证重复执行结果一致。锁是过程控制，幂等是结果正确性保障。生产中两者常常一起用，但幂等比锁更底层、更重要。

---

### Q20：乐观锁和悲观锁怎么选？

**回答抓手：**

冲突少、读多写少，用乐观锁，比如 version 字段或 CAS；冲突多、强一致要求高，用悲观锁。高并发系统一般优先减少锁粒度和锁时间。

---

## 4. Redis 队列与异步任务

### Q21：为什么要用队列？

**回答抓手：**

队列用于异步解耦、削峰填谷、失败重试、任务缓冲和提升接口响应速度。Agent 场景里，视频生成、代码扫描、批量报告、消息通知都适合异步队列。

---

### Q22：Redis List 能不能做队列？

**回答抓手：**

可以，用 `LPUSH + RPOP` 或 `RPUSH + BLPOP` 实现简单队列。优点是简单、性能高；缺点是缺少完善的消费确认、重试、消费组和消息追踪能力。复杂场景建议用 Redis Stream 或专业 MQ。

---

### Q23：Redis Stream 相比 List 有什么优势？

**回答抓手：**

Stream 支持消息 ID、消费组、消费者、ACK、Pending List、消息回溯，更适合做可靠消息队列。List 更像简单队列，Stream 更接近轻量 MQ。

---

### Q24：Redis Stream 怎么保证消息不丢？

**回答抓手：**

生产者写入后消息保存在 Stream 中；消费者读取后需要 ACK；未 ACK 的消息进入 Pending List，可以被重新认领和消费。还要配置持久化、监控 pending 消息、处理死信。

---

### Q25：Redis Stream 会不会重复消费？

**回答抓手：**

会。网络超时、消费者崩溃、ACK 丢失、消息重新认领都可能导致重复消费。所以消费者业务必须幂等，不能假设消息只会被消费一次。

---

### Q26：Redis 队列和 Kafka/RabbitMQ 怎么选？

**回答抓手：**

Redis 队列适合轻量异步任务、低延迟、系统已有 Redis 的场景；Kafka 适合高吞吐日志流、事件流、可回放场景；RabbitMQ 适合复杂路由、确认机制和业务消息。不能把 Redis 当万能 MQ。

---

### Q27：延迟队列怎么用 Redis 实现？

**回答抓手：**

常见方案是 ZSet，score 存执行时间戳，消费者定时扫描 score 小于当前时间的任务，再抢占执行。要注意并发抢占、原子删除、失败重试和时间精度。

---

### Q28：Redis 延迟队列有什么问题？

**回答抓手：**

问题包括扫描压力、时间精度有限、任务过多时性能下降、消费者并发抢占、没有天然 ACK 和死信机制。复杂业务可以考虑专业 MQ 或任务调度系统。

---

### Q29：队列积压怎么排查？

**回答抓手：**

从生产速度、消费速度、消费者数量、单任务耗时、下游依赖、失败重试、锁竞争、数据库慢查询、外部 API 限流几个方向排查。核心指标是队列长度、消费延迟、失败率和平均处理耗时。

---

### Q30：如何处理死信任务？

**回答抓手：**

任务多次失败后进入死信队列，记录失败原因、上下文、重试次数和负责人。死信可以人工处理、定时补偿、修复后重放。不能无限重试把系统打爆。

---

### Q31：异步任务如何做状态机？

**回答抓手：**

常见状态：待处理、处理中、成功、失败、重试中、已取消、死信。状态流转要持久化，更新要幂等。长任务 Agent 不能只靠内存状态。

---

### Q32：视频生成 Agent 任务队列怎么设计？

**回答抓手：**

用户提交任务后先落库，返回 taskId；任务进入队列；worker 拉取任务后更新为处理中；执行脚本生成、分镜、模型调用、质检、发布等步骤；每一步保存状态和中间产物；失败可重试或转人工；前端通过轮询、WebSocket 或 SSE 查看进度。

---

## 5. 高并发限流、削峰、降级

### Q33：高并发系统怎么做限流？

**回答抓手：**

常见算法包括固定窗口、滑动窗口、漏桶、令牌桶。限流可以在网关、服务层、用户维度、接口维度、租户维度做。大模型服务尤其要按 token、QPS、并发数和成本预算限流。

---

### Q34：令牌桶和漏桶有什么区别？

**回答抓手：**

令牌桶允许一定突发流量，只要桶里有令牌就能通过；漏桶强调固定速率流出，更平滑。接口防突刺常用令牌桶，下游保护和稳定输出常用漏桶思想。

---

### Q35：什么是削峰填谷？

**回答抓手：**

把瞬时高流量先写入队列，消费者按系统可承受速度处理，避免请求直接打爆数据库、模型 API 或外部工具。代价是实时性下降，所以要区分同步和异步场景。

---

### Q36：什么是熔断和降级？

**回答抓手：**

熔断是在下游持续失败时暂时停止调用，避免故障扩散；降级是在能力不足时返回简化结果、缓存结果或提示稍后处理。Agent 系统里模型不可用、工具不可用、RAG 不可用都要设计降级。

---

### Q37：如何保护大模型 API 不被打爆？

**回答抓手：**

按用户、租户、接口、模型和任务类型限制 QPS、并发、token、费用。对高耗时任务走异步队列；对重复请求做缓存；对低优先级任务排队；对异常流量熔断和风控。

---

### Q38：接口超时怎么设计？

**回答抓手：**

要分层设置超时：网关超时、服务超时、数据库超时、Redis 超时、外部 API 超时、模型 API 超时。超时后要有取消、重试、降级或任务异步化，不能无限等待。

---

### Q39：如何设计一个高并发秒杀系统？

**回答框架：**

前端限流和验证码 → 网关限流 → Redis 预扣库存 → 请求入队 → 异步创建订单 → 数据库最终落库 → 超时未支付回滚库存。重点讲库存一致性、幂等、防重复下单、削峰和异步化。

---

### Q40：Agent 平台如何做并发隔离？

**回答抓手：**

按租户、用户、模型、工具、任务类型做资源池隔离。高成本任务和低成本任务分队列；高优先级客户独立限额；失败任务不能影响正常任务。要监控每个队列的积压和耗时。

---

## 6. 分布式事务与一致性

### Q41：什么是分布式事务？

**回答抓手：**

分布式事务是一次业务操作涉及多个服务或多个数据源，需要保证它们的状态一致。常见方案包括 2PC、TCC、本地消息表、事务消息、Saga、补偿机制、最终一致性。

---

### Q42：强一致和最终一致怎么选？

**回答抓手：**

资金、库存扣减、权限变更等高风险场景倾向强一致；消息通知、搜索索引、统计报表、推荐结果可以最终一致。大多数互联网系统会在关键链路强一致，非关键链路最终一致。

---

### Q43：本地消息表怎么保证最终一致？

**回答抓手：**

业务数据和消息记录在同一个本地事务里写入数据库；后台任务扫描未发送消息并投递 MQ；消费者幂等处理；失败可重试。优点是可靠，缺点是链路较长，有延迟。

---

### Q44：Saga 模式是什么？

**回答抓手：**

Saga 把一个大事务拆成多个本地事务，每一步都有对应补偿动作。某一步失败时，按相反顺序执行补偿。适合长流程业务，但要求补偿动作设计清楚。

---

### Q45：Agent 长任务如何保证最终一致？

**回答抓手：**

把任务拆成多个可恢复步骤，每一步状态落库；工具调用有幂等 key；失败后根据状态继续执行或补偿；最终结果由状态机驱动，不能只依赖一次模型调用成功。

---

### Q46：如何处理重复消息？

**回答抓手：**

消费者端做幂等，比如业务唯一键、消费记录表、Redis 去重、数据库唯一索引、状态机判断。不要假设 MQ 或 Redis 队列能保证严格一次消费。

---

### Q47：如何处理消息乱序？

**回答抓手：**

可以按业务 key 分区、同一 key 串行消费、消息带版本号、状态机校验。对要求严格顺序的业务，不能让同一业务对象被多个消费者并发处理。

---

### Q48：如何设计补偿机制？

**回答抓手：**

补偿要记录原始请求、执行状态、失败原因、重试次数、下一次重试时间。补偿任务要幂等，并支持人工介入。补偿不是简单重试，而是恢复业务一致性。

---

## 7. Redis 高可用与持久化

### Q49：Redis 持久化方式有哪些？

**回答抓手：**

主要有 RDB 和 AOF。RDB 是快照，恢复快但可能丢最近数据；AOF 记录写命令，数据更完整但文件更大、恢复可能更慢。生产中常结合使用。

---

### Q50：Redis 主从复制有什么用？

**回答抓手：**

用于读写分离、数据备份和高可用基础。主节点负责写，从节点复制数据并承担部分读流量。要注意复制延迟和主从不一致。

---

### Q51：Redis Sentinel 解决什么问题？

**回答抓手：**

Sentinel 用于监控 Redis 主从节点，在主节点故障时自动选举新的主节点，并通知客户端更新连接。它解决高可用问题，但不解决横向分片扩容问题。

---

### Q52：Redis Cluster 解决什么问题？

**回答抓手：**

Redis Cluster 通过 slot 分片实现数据水平扩展，同时支持主从高可用。它适合数据量和并发都较高的场景，但会带来多 key 操作限制和运维复杂度。

---

### Q53：Redis 内存满了怎么办？

**回答抓手：**

可以设置 maxmemory 和淘汰策略，比如 allkeys-lru、volatile-lru、allkeys-lfu 等。还要从业务上控制大 Key、过期时间、冷热数据分层和容量监控。

---

### Q54：Redis 慢查询怎么排查？

**回答抓手：**

查看 slowlog、命令复杂度、大 Key、网络延迟、CPU、内存、持久化阻塞、Lua 脚本耗时。避免在线上使用 keys、大范围 scan、超大集合操作。

## 8. Agent 项目里的高并发设计题

### Q55：设计一个高并发 Agent 任务执行平台。

**回答框架：**

用户请求先落库生成 taskId；轻任务同步返回，重任务进入队列；调度器按租户、优先级和任务类型分发；worker 执行工具调用和模型调用；每一步写状态机；失败重试进入死信；全链路 trace；按用户和租户做并发、token、成本限流。

---

### Q56：设计一个视频生成任务队列。

**回答框架：**

前端提交任务 → 后端校验权限和额度 → 任务入库 → Redis Stream / MQ 入队 → Worker 分阶段处理脚本、分镜、素材、生成、质检、发布 → 每阶段状态落库 → 失败按阶段重试 → 最终结果通知用户。

---

### Q57：设计一个 Agent 工具调用限流系统。

**回答框架：**

按照工具风险等级和成本设置不同限流策略。只读工具可高并发，写工具低并发，高风险工具需要确认。维度包括用户、租户、工具、模型、IP、任务类型。超过限制后排队、降级或拒绝。

---

### Q58：设计一个 Agent 记忆缓存系统。

**回答框架：**

短期上下文放 Session Store，热点用户记忆放 Redis 缓存，长期记忆放数据库/向量库/搜索索引。更新时先写主存储，再删缓存。检索时做权限过滤和版本校验，避免读到过期记忆。

---

### Q59：设计一个防重复执行的 Agent 工具系统。

**回答框架：**

每次工具调用生成 requestId 和 idempotencyKey；执行前查幂等表；处理中直接返回当前状态；成功返回历史结果；失败根据失败类型决定是否重试。副作用工具必须记录执行状态和结果。

---

### Q60：设计一个 K8s 告警分析 Agent 的异步处理架构。

**回答框架：**

告警进入系统后生成事件 ID；相同服务和规则短时间内聚合去重；任务入队；Agent 查询指标、日志、事件和发布记录；结果写入告警分析表；严重告警通知负责人；重复告警走冷却时间，避免消息风暴。

---

## 9. 面试回答模板

### 9.1 回答 Redis 队列题

```text
我会先区分这个队列对可靠性的要求。
如果只是轻量异步任务，可以用 Redis List；
如果需要消费组、ACK、Pending 和消息回溯，我会优先考虑 Redis Stream；
如果是高吞吐事件流或强消息能力，就会考虑 Kafka/RabbitMQ。
无论哪种队列，消费者都必须做幂等，因为重复消费几乎不可避免。
```

### 9.2 回答高并发题

```text
我一般从四层回答：
1. 入口层限流：网关、用户、租户、接口维度；
2. 缓存层抗压：热点缓存、本地缓存、缓存预热；
3. 队列层削峰：异步化、优先级队列、失败重试；
4. 数据层兜底：幂等、唯一索引、状态机、补偿机制。
```

### 9.3 回答 Agent + 分布式题

```text
Agent 系统不能只看模型效果，还要看运行时工程能力。
例如一个视频生成 Agent，要把长任务拆成多个状态节点，
用队列削峰，用 Redis 或数据库记录任务状态，
对模型调用和工具调用做限流、重试、幂等和 trace，
这样失败后才能恢复，线上问题也能定位。
```

## 10. 最适合背下来的高频一句话

- 缓存穿透：查不存在的数据，每次都打 DB。
- 缓存击穿：热点 Key 过期，大并发打 DB。
- 缓存雪崩：大量 Key 同时失效或 Redis 挂了。
- 分布式锁：控制并发进入临界区，但不能替代幂等。
- 幂等：重复执行，最终结果一致。
- Redis List：适合简单队列。
- Redis Stream：适合带 ACK 和消费组的可靠队列。
- 延迟队列：常用 ZSet，score 存执行时间。
- 队列积压：看生产速度、消费速度、任务耗时和下游瓶颈。
- 死信队列：多次失败后隔离，避免无限重试。
- Agent 长任务：必须状态机化、异步化、可恢复。
